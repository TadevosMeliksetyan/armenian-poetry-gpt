# Armenian poetry GPT

A small GPT that writes Armenian poetry in the style of Paruyr Sevak. I trained it from scratch in Google Colab, starting from a character-level model and ending with a BPE model of about 34M parameters.

I started from Andrej Karpathy's ["Let's build GPT"](https://www.youtube.com/watch?v=kCc8FmEb1nY) video. The first version was basically that model trained on 2M characters of Armenian poems. After that I kept changing one thing at a time and measuring the result. This README is mostly a log of those changes and what each one gave.

In the next part I fine-tune bigger pretrained models with LoRA on the same data and compare them with my model.

## Why Sevak

I picked Sevak because I love his poetry style and, which is very important, he wrote much more than others, which is a good opportunity for the model. At first I thought that small models like mine can't feel Sevak's style, and nothing can, but it was very surprising that arm-gemma-e4b with LoRA can imitate him so closely. Also I was surprised that my GPT model (60M) generated smoother and more grammatical text, even though its val loss was not better.

## How it works

Training goes in three stages. Every stage starts from the best weights of the previous one:

| Stage | Data | Size |

| 1. Pretraining | Armenian prose (Wikisource books + Wikipedia) | 200M characters |
| 2. Poetry | poems by many Armenian poets (Sevak removed) | 6.4M characters |
| 3. Fine-tuning | Paruyr Sevak | 0.86M characters |

Sevak's text is kept out of stages 1 and 2. I checked line overlap between Sevak and the other poetry files and found 1 to 11 lines out of 21,431, depending on the file, so the Sevak validation loss is honest.

### Data

Everything comes from public dumps of Armenian Wikisource and Wikipedia. The cleaning took more time than anything else:

- only 104 characters are allowed (Armenian letters, Armenian punctuation, digits, a few symbols). Other characters are either mapped (`:` -> `։`, `…` -> `...`) or the line is dropped
- texts in classical orthography are removed (`ւ` without `ո` before it is a good marker)
- Western Armenian is removed with a small word-frequency test (`կը`, `մը`, `-ներու` and similar). Eastern texts score ~0, Western ones 28-48
- OCR errors in scanned books (Latin `n` instead of `ո`, `o` instead of `օ`, etc.) are fixed
- duplicate paragraphs are removed, and wrapped lines in scanned pages are joined back

In the end there were 88M characters of literature, 70M of encyclopedic text and 346M of Wikipedia. The corpus itself is not in this repo (see [Copyright](#copyright)).

### Tokenizer

BPE with 8192 tokens, trained on my own corpus with the Hugging Face `tokenizers` library. Before counting pairs, the text is split into words, and a space sticks to the start of a word (` եմ`). Without that, the most frequent pair in Armenian is "space + first letter", and merges start crossing word borders.

Even a slow pure-Python version of the algorithm, with only 500 merges on 2M characters, already learns `ու`, `ում`, `ներ`, `ություն` and splits ` սիրում` into ` սիր` + `ում`.

Characters per token for different vocab sizes:

| vocab | prose | Sevak |
|---|---|---|
| 2048 | 2.91 | 2.30 |
| 4096 | 3.29 | 2.51 |
| **8192** | **3.66** | **2.71** |
| 16384 | 4.02 | 2.90 |
| 32768 | 4.35 | 3.08 |

Compression keeps getting better with a bigger vocab and there is no point where it suddenly stops, so I picked 8192 to keep the embedding and output layers small compared to the rest of the model. Poetry compresses much worse than prose, probably because poems have rarer words and the tokenizer saw mostly prose.

### Model and training

The model is a decoder-only transformer close to GPT-2: 8 layers, 512 dim, 8 heads (head size 64), context of 256 tokens (~900 characters of prose), pre-LayerNorm, learned position embeddings, ReLU MLP, ~33.7M parameters. Attention goes through `F.scaled_dot_product_attention` (flash attention).

Training uses AdamW with linear learning rate decay and early stopping on validation loss, in bf16 autocast. The whole dataset sits on the GPU as an `int16` tensor and batches are cut with a single indexing operation. Checkpoints go to Google Drive at every eval, so a run can continue after Colab disconnects.

| Stage | lr | dropout | max steps |
|---|---|---|---|
| prose | 1e-3 -> 5e-5 | 0.0 | 30000 |
| poetry | 3e-4 -> 3e-5 | 0.2 | 2000 |
| Sevak | 1e-4 -> 1e-5 | 0.2 | 400 |

## Experiments

Losses with different tokenizers can't be compared directly, so the table uses validation loss **per character** (loss per token / characters per token).

| Change | Model | Prose val | Sevak val |
|---|---|---|---|
| char-level, poetry only | 10.8M | - | ~1.48* |
| + 100M prose pretraining | 10.8M | 1.18 | 1.337 |
| dropout 0.2 -> 0.0 on prose | 10.8M | 1.10 | |
| BPE 8192 | 17.0M | 1.04 | 1.356 |
| prose 100M -> 200M | 17.0M | ** | 1.342 |
| bigger model (6x384 -> 8x512) | 33.7M | | **1.305** |
| bigger model + more prose (10x640, 500M characters) | 60M | | 1.311 |

\* different validation split, only roughly comparable
\** the validation set changed with the data (much more Wikipedia), so the number is not comparable. What did change clearly is the train/val gap: 0.59 -> 0.13.

Pretraining on prose helped a lot. Before any training on Sevak, the pretrained model already had lower loss on Sevak than my old model fine-tuned on him.

Dropout only slowed things down on prose. With 100M characters train and val loss were almost equal, so there was nothing to regularize. On poetry it is needed.

The train/val gap told me what to do next every time. With BPE the same 30000 steps became ~18 epochs and the model started memorizing (gap 0.59). Doubling the data fixed it, after that the model was the bottleneck and making it bigger gave the biggest gain on Sevak. But then it stopped: the 60M model on 2.5x more prose got the same Sevak loss as the 34M one. Most of the extra prose was Wikipedia, which is far from poetry, and there is just not much Sevak text to fine-tune on.

One accident: I ran the poetry stage of the 60M model with lr 1e-3 instead of 3e-4 by mistake, and it was better (1.311 vs 1.364 on Sevak). So the settings from the smaller model were not right for the bigger one.

### Longer context?

Before trying a longer context I measured the validation loss separately for every position in the 256-token window (Sevak model, 50 batches):

| position | 0 | 10 | 50 | 100 | 150 | 255 |
|---|---|---|---|---|---|---|
| loss | 4.82 | 3.67 | 3.55 | 3.52 | 3.48 | 3.54 |

After ~100 tokens (about 10 lines of Sevak) the loss stops going down. The model doesn't use the context it already has, so a longer window would not help. I kept 256.

### Speed

| Change | Time for 30000 prose steps |
|---|---|
| manual attention, one head at a time, fp32 | 23 min |
| `scaled_dot_product_attention` | 17 min |
| + bf16 autocast | about 4x faster |

bf16 helped more than I expected. It lets matmuls run on tensor cores, and the fastest flash attention kernel only works in fp16/bf16, so the 23 -> 17 step was not real flash attention yet.

## Bugs I hit

Each of these took me a while to find:

- **Flat loss in fine-tuning.** I created a new model in a generation cell and didn't recreate the optimizer. The optimizer kept updating the old model, and the loss didn't move for 160 steps.
- **Wrong attention scaling.** I divided by `sqrt(n_embed)` instead of `sqrt(head_size)`. It still trained, the model just compensated with bigger weights.
- **Dropout during generation.** After training the model stays in train mode. Without `m.eval()` the samples were worse than the model really is.
- **`view` on a sliced tensor.** `chunk[:, 1:]` is not contiguous, so `.view()` fails; `.reshape()` works.
- **`uint8` was fine for 104 characters, not for 8192 tokens.** The token ids are stored as `int16` now.

## Part 2: fine-tuning a pretrained model with LoRA

After finishing my own model I wanted to know how far it is from a real pretrained LLM. I took several open models and measured them on exactly the same Sevak validation text, also per character, so the numbers can be compared with part 1.

| model | chars / token | Sevak val (per char) |
|---|---|---|
| Qwen3-1.7B-Base | 1.02 | 1.526 |
| Qwen3-4B-Base | 1.02 | 1.425 |
| Qwen3-8B-Base | 1.02 | 1.325 |
| Gemma 3 1B | 1.64 | 1.526 |
| Gemma 3 4B | 1.64 | 1.293 |
| Gemma 3 12B | 1.64 | 1.160 |
| arm-gemma-e4b (Gemma 4 E4B + extra Armenian pretraining) | 1.64 | 1.036 |
| my model, after fine-tuning on Sevak | 2.71 | 1.305 |

These are before any fine-tuning. Qwen's tokenizer has almost no Armenian in it, one token is about one letter.

If a model saw Sevak's poems during pretraining, a low loss means nothing. So I gave it two real lines from the validation text and let it continue without sampling. In 30 random places, Gemma 3 12B and arm-gemma reproduced 0 of the next lines, not even the first three words.

### LoRA

LoRA keeps the model weights frozen and learns a small update `B @ A` next to each layer. `B` starts at zero, so at step 0 the model is exactly the original one. That was an easy check, the first validation loss was always the same as in the table above. Rank 16, alpha 32, all attention and MLP layers, lr 2e-4, batch 8 x 512 tokens, trained only on the Sevak training split.

| model | before | after LoRA |
|---|---|---|
| Gemma 3 4B | 1.293 | 1.174 |
| Gemma 3 12B | 1.160 | 1.065 |
| arm-gemma-e4b | 1.036 | **1.010** |

The 8B model with extra Armenian pretraining beats the 12B one even after LoRA, so for Armenian the language data matters more than size. LoRA also gave much less to arm-gemma (0.026) than to Gemma 3 12B (0.095), I think because it already knew a lot of what Sevak's text could teach it. Both Gemma 3 models had their best step at 150, which is about one pass over Sevak's text, after that they started to overfit.

The 12B model needed gradient checkpointing even on a 96 GB GPU. And Gemma 4 is multimodal, so LoRA has to target only the language layers; its image and audio layers are a different type and PEFT fails on them.

Sample from arm-gemma-e4b + LoRA, prompt `Հայաստան`, temperature 0.8, top-k 50:

```
Հայաստանը, իմ երկիրը։

Իմ Հայաստանը, իմ երկիրը՝
Ուղն ու ծուծով իմ Հայաստանը
Ինձնից բաժանվեց այնպես դաժան,
Ինչպես որ թե բաժանվում են երկու թիվ
Որոնման մեջ,
Բայց ոչ հավասարության մեջ։

-Իմ Հայաստանը, իմ երկիրը։

Ինչքա՛ն քաղցր է այնտեղ, որտեղ դու ես։
Բայց ես քաղցրությունից, ո՛չ, չե՛մ խենթանում։

```

### Synthetic data for my small model

The big model is much better than mine, so I tried to use it as a teacher. arm-gemma + LoRA generated ~1M characters in the style of Sevak, with first lines from the Sevak training split as prompts. From that I removed everything close to Sevak's real lines (the same line, or 6 words in a row), poems that loop on one line, and duplicates, and 962K characters were left. The generated text is flatter than the real one, it has 18% fewer distinct words. It is not in this repo either, for the same copyright reason.

Results for the 60M model (poetry stage with lr 3e-4):

| path | Sevak val (per char) |
|---|---|
| poetry -> Sevak | 1.364 |
| poetry -> synthetic -> Sevak | 1.344 |
| poetry -> Sevak -> synthetic -> Sevak | 1.360 |

Synthetic text before Sevak helped a little, after Sevak it did almost nothing, and it still did not beat my best model from part 1 (1.305). Each number is one run, so I would not trust a difference of 0.02 too much.

## Running it

Everything runs in Colab.

**Part 1** [![Open in Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/TadevosMeliksetyan/armenian-poetry-gpt/blob/master/armenian_gpt.ipynb) `armenian_gpt.ipynb` expects these files in `MyDrive`:

- `tokenizer_8192.json` (in this repo)
- the encoded data: `prose_200M_bpe8192.pt`, `poetry_stage2_bpe8192.pt`, `sevak_bpe8192.pt` (not in this repo)

For each stage, set `TEXT_FILE` (the `.txt` name, the notebook loads the matching `_bpe8192.pt`) and the hyperparameters in the first cell, and `RUN` / `INIT_FROM` in the training cell. If `RUN` already has a checkpoint, training continues from it.

**Part 2** [![Open in Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/TadevosMeliksetyan/armenian-poetry-gpt/blob/master/lora_finetune.ipynb) `lora_finetune.ipynb` needs `tokenizer_8192.json` and `sevak_bpe8192.pt` in `MyDrive`, and a Hugging Face token with access to Gemma. Gemma 3 12B needs the large GPU. Each section can be run on its own after the setup cells.
